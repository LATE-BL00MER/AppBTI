# 통합 테스트 체크리스트 초안 — 11/16 기능 동결 점검용

기준은 [공통 지침](../AGENTS.md), [API 계약](API.md), [실행 안내](../README.md)다. 아직 실행하지 않은 항목은 체크하지 않는다. 점검 결과에는 성공·실패와 실패 단계만 적고 실제 데이터 수치는 남기지 않는다.

명령은 저장소 루트에서 실행한다. 폴더를 바꾸는 명령은 괄호로 감싸 실행 후 루트로 돌아온다. API는 `http://127.0.0.1:8080/api` 기준이며 브라우저 개발자도구의 Network에서도 응답을 확인한다. POST 오류 검사는 목업 설문 제출 요청을 Network에서 `Copy as cURL`로 복사한 뒤 해당 필드만 바꿔 재전송한다. 문항 코드는 `/survey/questions`가 반환한 값을 사용한다.

현재 목업 비교 설정으로 확인할 항목과 회의 후 실제 설정으로 다시 확인할 항목을 구분한다. 실제 유사도 설정이 비활성화된 동안에는 설문·결과 정상 비교 통과로 처리하지 않고 탐색 안내를 확인한다. 회의 결정에 의존하는 항목은 마지막 절에 모았다.

## 1. 준비

- [ ] Python 환경 — 확인 방법: README의 Python 3.11 가상환경 설치 명령을 실행하고 `pipeline/.venv/bin/python --version`이 3.11인지 확인한다.
- [ ] 목업 준비 — 확인 방법: `./scripts/prepare-demo.sh`가 두 목업 산출물·백엔드 JAR·프론트 의존성을 준비하고 종료 코드 0으로 끝나는지 확인한다.
- [ ] 실행 위치 독립성 — 확인 방법: `/tmp`에서 작업트리의 `scripts/prepare-demo.sh`를 절대 경로로 실행하고 종료 코드 0인지 확인한다.
- [ ] 실제 데이터 준비 — 확인 방법: 저장소 밖 `~/appbti-data/raw/real/`의 원본을 Orca 설정 스크립트로 `data/raw/real/`에 복사한 뒤 `./scripts/prepare-demo.sh --real`의 성공 여부를 확인하고, 실패하면 수용 검사 단계를 기록한다.
- [ ] 실제 데이터 누락 안내 — 확인 방법: 실제 원본이 없는 별도 작업트리에서 `./scripts/prepare-demo.sh --real`을 실행하고 외부 보관·Orca 복사 안내와 종료 코드 1을 확인한다.
- [ ] 목업 백엔드 기동 — 확인 방법: 별도 터미널에서 `(cd backend && java -jar build/libs/appbti-backend-0.1.0-SNAPSHOT.jar)`를 실행하고 `/api/meta`의 `isMock=true`인지 확인한다.
- [ ] 프론트 기동 — 확인 방법: 별도 터미널에서 `(cd frontend && npm run dev)`를 실행하고 `http://127.0.0.1:5173`의 홈과 `/api/meta` 프록시 응답이 열리는지 확인한다.
- [ ] 목업 HTTP 검증 — 확인 방법: 목업 서버 둘이 켜진 상태에서 `pipeline/.venv/bin/python scripts/check_demo.py`를 실행해 HTTP 검사 26개 통과와 종료 코드 0을 확인한다(실제 데이터 서버에서는 실행하지 않는다).
- [ ] 실제 데이터 전환 — 확인 방법: 목업 백엔드를 종료한 뒤 `(cd backend && APPBTI_PROFILES_PATH=../data/processed/real/profiles.json java -jar build/libs/appbti-backend-0.1.0-SNAPSHOT.jar)`로 재기동하고 `/api/meta`의 `isMock=false`와 실제 제공처 집단 정의를 확인한다.
- [ ] 서버 종료 — 확인 방법: 점검 종료 후 백엔드·프론트 터미널에서 각각 `Ctrl+C`를 누르고 8080·5173 포트의 검증 서버가 종료됐는지 확인한다.

## 3. API

- [ ] 메타 정보 — 확인 방법: `GET /api/meta`에서 `isMock`이 현재 데이터와 일치하고 `months`가 제공 기간을 나타내며 `ageGroups`가 6개인지 확인한다(목업 A~F, 실제는 20대 미만·20대·30대·40대·50대·60대 이상).
- [ ] 실제 기간·데이터 분리 — 확인 방법: 실제 모드의 `/api/meta`에서 기간이 2025년 1~6월이고 `availableDatasets`에 목업 시간 버전이 섞여 있지 않은지 확인한다.
- [ ] 최신월 기본값 — 확인 방법: `GET /api/profiles`의 `month`가 `/api/meta`의 최신월과 같고 해당 월을 명시한 `GET /api/profiles?month=<최신월>`과 같은 행을 반환하는지 확인한다.
- [ ] 추이의 빠진 달 — 확인 방법: 목업 `GET /api/profiles/trend?minor=travel&dataset=basic`에서 빠진 달의 행이 보존되고 지표가 `null`이며 `status=missing`인지 확인한다.
- [ ] 추이의 집계 경계 — 확인 방법: `/api/profiles/trend`의 `continuityBreaks`와 행의 `segment`를 확인하고 코드북에 기준 변경이 있는 경우 해당 경계를 구분하는지 확인한다.
- [ ] 설문 정의 — 확인 방법: `GET /api/survey/questions`의 `month`·`maxDays`가 기준월과 맞고 모든 `minorCode`가 현재 코드북의 중분류에 연결되며 `minimumCategories`·`zeroDaysPolicy`·`timeAvailable`이 설정과 일치하는지 확인한다.
- [ ] 정상 비교 — 확인 방법: 목업에서 비교 가능한 문항을 최소 개수 이상 답해 `POST /api/survey/result`가 HTTP 200·`status=comparable`·6개 집단 전체 점수·닮은 항목과 다른 항목 근거를 반환하는지 확인한다.
- [ ] 비교 부족 — 확인 방법: `POST /api/survey/result`에 `{"answers":[]}`를 보내 HTTP 200·`status=insufficient`·빈 `scores`와 이유가 반환되는지 확인한다.
- [ ] 음수 거부 — 확인 방법: 정상 목업 요청의 등록 문항 하나를 `days=-1`로 바꿔 재전송하고 HTTP 400과 `message`를 확인한다.
- [ ] 월 일수 초과 거부 — 확인 방법: 정상 목업 요청의 `days` 하나를 `/api/survey/questions`의 `maxDays`보다 1 크게 바꿔 재전송하고 HTTP 400을 확인한다.
- [ ] 중복 문항 거부 — 확인 방법: 정상 목업 요청의 같은 `minorCode` 답변을 두 번 넣어 재전송하고 HTTP 400을 확인한다.
- [ ] 미등록 문항 거부 — 확인 방법: 정상 목업 요청의 문항 코드를 문항 목록에 없는 `unknown-test-minor`로 바꿔 재전송하고 HTTP 400을 확인한다.
- [ ] 무응답·사용 안 함 구분 — 확인 방법: 동일 문항에 `days=null`과 `days=0`을 각각 보내 무응답은 제외되고 0일은 `/api/meta`의 `zeroDaysPolicy`에 따라 처리되며 두 입력의 의미가 구분되는지 확인한다.
- [ ] 결정적 결과·동점 — 확인 방법: 같은 목업 요청을 두 번 보내 응답 JSON이 같고 동점이 있는 경우 집단 ID 순서와 공동 표시가 일정한지 확인한다.
- [ ] 결측 보존 — 확인 방법: 목업 `/api/profiles?dataset=basic`의 비공개·누락 행과 `minor=news`의 구성비를 확인해 지표가 `null`이며 0으로 채워지지 않는지 확인한다.

## 4. 화면 흐름

- [ ] 정상 흐름 — 확인 방법: 홈의 ‘내 패턴 알아보기’ → 설문 응답 → 결과 제출 → 결과의 ‘집단별 통계 자세히 보기’ 순서로 이동해 설문·결과·세대별 탐색이 오류 없이 이어지는지 확인한다(현재는 목업, 회의 후 실제 설정으로 반복).
- [ ] 결과 근거 — 확인 방법: 결과에서 전체 집단 순위와 닮은·다른 중분류를 펼쳐 사용자 응답과 같은 기준월의 집단 통계를 비교할 수 있는지 확인한다.
- [ ] 응답 수정 — 확인 방법: 결과의 ‘응답 수정하기’ → 기존 답변 확인 → 한 항목 수정 → 재제출 후 수정한 응답으로 근거가 갱신되는지 확인한다.
- [ ] 다시 하기 — 확인 방법: 결과의 ‘처음부터 다시 하기’를 눌러 설문 응답과 이전 결과가 초기화되고 새 설문을 시작할 수 있는지 확인한다.
- [ ] 비교 부족 안내 — 확인 방법: 목업에서 한 문항만 답하고 결과를 제출해 부족 사유·‘응답 이어서 작성하기’·‘세대별 탐색하기’가 보이고 두 링크가 동작하는지 확인한다.
- [ ] 비교 비활성 안내 — 확인 방법: 실제 비교 설정이 비활성인 상태에서 설문에 진입해 비교 기준 준비 안내가 보이고 세대별 탐색으로 이동할 수 있는지 확인한다.
- [ ] 탐색 조작·추이 — 확인 방법: 세대별 탐색에서 중분류 → 기준월 → 사용 가능한 지표 → 집단 강조를 바꿔 차트·표·출처가 함께 갱신되고 결측·집계 경계를 선으로 잇지 않으며 고립된 월은 점으로 보이는지 확인한다.

## 5. 문구·표시

- [ ] 금지 문구 — 확인 방법: 홈·설문·결과·탐색·데이터 안내에서 ‘당신은 20대입니다’, ‘디지털 나이’, ‘정확도 87%’, ‘일치 확률’, ‘이용률’, ‘○○대가 가장 많이 쓰는’ 등의 단정·과장 표현이 없는지 읽어 확인한다(정확도·확률이 아니라는 설명은 허용).
- [ ] 목업 배지 — 확인 방법: `/api/meta`의 `isMock=true`일 때 화면 상단에 ‘예시 데이터’가 보이고 실제 모드에서는 해당 배지가 사라지는지 확인한다.
- [ ] 출처·범위 — 확인 방법: 실제 집단 통계 옆에 LG U+ 제공 연령대·기간(2025년 1~6월) 집계라는 출처·범위와 해당 기준월이 표시되는지 확인한다.
- [ ] 결측 표시 — 확인 방법: 목업 뉴스 읽기·여행/나들이의 비공개·누락 사례를 차트와 표에서 찾아 ‘데이터 없음’이 보이고 임의의 0이 표시되지 않는지 확인한다.
- [ ] 결과 해석 — 확인 방법: 결과가 자기보고 응답과 집단 통계의 ‘패턴 유사도’ 비교라고 설명하고 실제 나이 추정이나 개인 실제 이용 기록 분석으로 읽히는 문구가 없는지 확인한다.
- [ ] 분류·구성비 표현 — 확인 방법: 결과·탐색에는 앱 이름 대신 중분류 이름이 나오고 구성비는 ‘이 분류 이용자 중 해당 연령대 비중’으로 설명되는지 확인한다(앱 예시는 설문에서만 허용).
