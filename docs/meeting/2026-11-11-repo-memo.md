## 2. 선택지

### A. 개인 레포 유지 + 팀원을 협업자로 추가
- 장점: 지금 바로 가능, 기존 PR·이력·Orca 설정 그대로
- 단점: **공개 레포**라 실제 데이터·수치가 한 번이라도 커밋되면 이력에 남고 바로 공개됨. 과목 조직 밖에 있어 제출·평가 기준과 맞지 않을 수 있음

### B. 팀 레포로 이력 그대로 옮기기 (`git push`로 main과 진행 중 브랜치 이동)
- 장점: **비공개**라 데이터 유출 위험이 줄어듦. 과목 조직 안에 있어 팀원·교수 접근 관리가 쉬움. 커밋 이력 유지
- 단점: GitHub PR(#5, #7)과 리뷰 코멘트는 옮겨지지 않음(커밋은 남음). 전원이 remote를 바꾸거나 새로 클론해야 함. Orca에 레포를 다시 등록해야 함

### C. GitHub "Transfer ownership"으로 개인 레포를 조직으로 이전
- 장점: PR·이슈까지 함께 이동, 옛 주소에서 자동 리다이렉트
- 단점: 조직에 레포 생성 권한이 필요함(확인 필요). 이미 만든 빈 `team_UplusTOPIA`와 이름이 달라 레포가 두 개가 되거나, 빈 레포를 지우고 이름을 맞춰야 함. 공개 여부는 이전 후 비공개로 따로 바꿔야 함

## 3. 추천안 (회의에서 확정)

**B안을 11/11 회의 직후에 한 번에 진행한다.**
- 이유: 비공개 저장소가 LG U+ 데이터 보호 조건에 가장 안전하다. 11/12부터 5명이 동시에 구현하므로 그전에 옮겨야 혼란이 적다. 기능 동결(11/16) 이후에는 옮기지 않는다.
- 순서
  1. 회의 중: 이전 여부와 시점 확정, 팀원 GitHub 아이디 수집
  2. 회의 직후(신진용): 팀 레포에 main과 진행 중인 `feat/*` 브랜치 push → 팀원 권한 부여(Write) → 개인 레포 README에 이전 안내 후 보관(Archive)
  3. 각자: `git remote set-url origin https://github.com/hansung-sw-capstone-2026-2/team_UplusTOPIA.git` (작업 중 브랜치는 그대로 이어서 push)
- 이전 후에도 `data/raw/`, `data/processed/`, 실제 수치가 담긴 파일·스크린샷은 **계속 커밋 금지**다. 비공개여도 LG U+ 데이터 사용 조건은 같다.

### 확인 필요
- 과목에서 팀 레포 사용이 제출·평가 요건인지 (요건이면 B 또는 C가 사실상 필수)
- 팀 레포에서 팀원 권한을 누가 줄 수 있는지 (조직 owner인지, 레포 admin으로 충분한지)
- 조직 플랜에서 **비공개 레포의 브랜치 보호 규칙**을 쓸 수 있는지. GitHub Free 조직은 비공개 레포 브랜치 보호가 제한될 수 있다. 안 되면 아래 규칙을 팀 약속으로 지킨다.

## 4. 브랜치 규칙 초안

| 항목 | 규칙 |
|---|---|
| 기본 브랜치 | `main` — 항상 시연 가능한 상태. 직접 push 금지, PR로만 머지 |
| 작업 브랜치 | `feat/<이름>-<작업>`, `fix/<이름>-<작업>`, `docs/<이름>-<작업>` (예: `feat/gibeom-explore-api`) |
| 브랜치 크기 | 하루 안에 머지할 수 있는 크기. 오래 걸리면 중간에 나눠 머지 |
| PR 리뷰 | 1명 승인 후 머지. 같은 영역 담당자 우선(백엔드 ↔ 백엔드, 데이터 ↔ 데이터), 영역을 넘는 변경은 해당 담당자가 승인 |
| 머지 방식 | Squash merge (PR 하나 = main 커밋 하나, 제목에 PR 번호) |
| 머지 전 확인 | 바뀐 영역 테스트 통과: `pytest` / `./gradlew test` / `npm run build` |
| 커밋 메시지 | 한국어, `feat(영역):`, `fix(영역):`, `docs:` 접두어, 무엇을 왜 바꿨는지 (AGENTS.md 12장) |
| 다른 사람 담당 파일 | 먼저 담당자에게 알리고, 커밋 메시지에도 적는다 |
| 충돌이 잦은 파일 | `docs/API.md`, `config/*.yaml`, `frontend/src/api/types.ts` — 수정 전에 단톡에 알린다 |
| 기능 동결(11/16) 이후 | `fix/*`만 머지. 팀장 승인 필요 |
| 발표 버전 | 11/17 리허설 통과 커밋에 `v-midterm` 태그. 시연은 이 태그로 |

### 회의에서 정할 것

- PR 승인자 규칙(1명 / 담당자 지정)
- 머지 방식(Squash / Merge commit)
- 동결 후 예외 승인 절차
