# REVIEW_GUIDE.md — 리뷰 절차와 체크리스트

어떤 에이전트든 이 문서로 리뷰한다.
- **모드 A (단독)**: 커밋 전에 3장 체크리스트로 자기 점검만 한다. `docs/REVIEW.md`에 기록할 필요는 없다.
- **모드 B (리뷰 루프)**: 리뷰 담당이 2장 절차대로 리뷰하고 5장 형식으로 `docs/REVIEW.md`에 쓴다. 리뷰 담당은 `docs/REVIEW.md` 외의 파일을 수정하지 않는다.
- **모드 C (Orca)**: 코디네이터가 작업자 결과를 3장 체크리스트로 점검한다.

장 번호는 `AGENTS.md`의 장을 가리킨다.

---

## 1. 우선순위

도메인 규칙(3장) → 일반 코드 품질(4장) 순으로 본다. **중간발표(11/18) 데모를 막는 문제가 가장 급하다.**

---

## 2. 리뷰 절차 (모드 B)

1. `git log --oneline -5`로 최근 커밋을 확인한다.
2. 리뷰 범위를 정한다.
   - 기본: `docs/REVIEW.md` 마지막 라운드에 적힌 커밋 이후
   - 처음이면: `git show HEAD`
3. `git diff <이전커밋>..HEAD`로 변경점을 읽는다. 변경된 함수가 쓰이는 곳도 필요하면 따라가서 읽는다.
4. 테스트가 있으면 실행한다(`scripts/review.ps1`로 호출된 경우는 6장 참고).
5. 이전 라운드에 `[반영 안 함: 이유]`가 있으면 그 이유를 검토한다. 타당하면 종결하고, 아니면 근거를 들어 다시 지적한다.
6. `docs/REVIEW.md`에 새 라운드를 쓴다(5장 형식).

---

## 3. 체크리스트 — 도메인 규칙 (가장 중요)

### 3-1. 지표 산식 (AGENTS.md 6장)
- [ ] 구성비, 기준일수(UU 가중 평균), 상대 빈도 산식이 6-1과 정확히 일치하는가
- [ ] 분모가 0이거나 결측일 때 `null`로 두는가 (0 나누기, Infinity, NaN 발생 여부)
- [ ] 기준일수가 **단순 평균**으로 계산돼 있지 않은가
- [ ] 기준일수가 "평균 이용일수 분모 = UU" 확인 전까지 설정 플래그로 분리돼 있는가
- [ ] 일부 연령대가 빠진 상태의 구성비에 "제공 연령 기준" 플래그가 붙는가
- [ ] 월별 변화가 분류·집계 기준이 바뀐 달을 가로질러 계산되지 않는가
- [ ] 대분류 점수가 문서화된 산식으로만 계산되는가

### 3-2. 금지 연산 (하나라도 있으면 **높음**)
- [ ] **서로 다른 중분류의 UU를 합산**해 대분류·전체 UU로 쓰고 있지 않은가
- [ ] UU나 구성비를 **이용률·보급률**로 계산·표현하지 않는가
- [ ] 평균 이용일수를 **더하거나 단순 평균**하지 않는가
- [ ] 이용일수·UU를 **이용시간으로 환산**하지 않는가
- [ ] 중분류 간 "이용시간 비중"이나 전체 Benchmark를 **가정해서 만들고** 있지 않은가
- [ ] 제공 6구간을 5세/10세 등으로 **임의 재분류**하지 않는가

### 3-3. 설문 비교 (AGENTS.md 7장)
- [ ] 설문 문항이 확정 문항 설정·코드북 중분류와 연결되는가 (하드코딩된 중분류 목록은 지적)
- [ ] "사용 안 함(0일)"과 "무응답"이 구분되고, 무응답은 비교에서 빠지는가
- [ ] 0일 응답 처리 방식이 설정으로 분리돼 있는가
- [ ] 이용시간 단위·정의가 확정되지 않았을 때 시간 비교가 꺼져 있는가
- [ ] 비교 조건이 부족할 때 세대별 탐색 화면으로 안내하는가

### 3-4. 결측·데이터 품질 (AGENTS.md 11장)
- [ ] 비공개·결측·빈칸·누락 행을 **0으로 바꾸는 코드가 없는가** (`fillna(0)`, `?? 0`, `|| 0`, `getOrDefault(..., 0)` 등)
- [ ] 원본에 status 컬럼이 없을 때 UU 0·빈 값을 결측으로 처리하는가
- [ ] '안전민감' 제외가 설정으로 되어 있고 사유가 문서화돼 있는가
- [ ] 수용 검사가 11장 항목을 다루는가
- [ ] 서로 다른 기준월의 값끼리 비교하고 있지 않은가
- [ ] API 응답에서 결측이 `null`로 내려가는가

### 3-5. 유사도·결과 (AGENTS.md 8장)
- [ ] 공통 중분류만 동일 척도로 정규화해 비교하는가
- [ ] 방식·가중치·유형이 설정으로 분리돼 있는가 (미확정 사항의 하드코딩은 지적)
- [ ] 동점·무응답·비교 불가 처리가 있는가
- [ ] **같은 입력에 같은 결과**가 나오는가 (무작위, 불안정 정렬, 객체 키 순서 의존 확인)
- [ ] 결과에 전체 순위와 가장 비슷한·가장 다른 중분류가 근거로 함께 나오는가
- [ ] 개인 군집화, 실제 연령 추정, 16유형·MBTI식 성격 유형이 구현돼 있지 않은가

### 3-6. UI 문구 (AGENTS.md 10장)
- [ ] "당신은 N대입니다", "디지털 나이", "정확도", "확률", "이용률", "○○대가 가장 많이 쓰는" 같은 표현이 없는가
- [ ] Figma에서 빼기로 한 요소(디지털 나이, 성향 스펙트럼, 시간대·푸시 분석, 출생연도, 근거 없는 수치)가 들어가지 않았는가
- [ ] 목업 데이터로 동작할 때 "예시 데이터" 표시가 있는가
- [ ] 집단 통계 옆에 출처·범위가 표시되는가
- [ ] 결과가 개인의 실제 이용 기록을 분석한 것처럼 보이지 않는가

### 3-7. 데이터 보안·교체 가능성 (AGENTS.md 12장)
- [ ] 실제 원본·파생 데이터, LG U+ 수치가 커밋되지 않았는가 (테스트 픽스처, 스크린샷, 로그 포함)
- [ ] 컬럼명 매핑이 코드북으로 분리돼 있는가
- [ ] 이용시간·중분류 코드가 없어도, 일부 월·연령대가 빠져도 코드가 깨지지 않는가
- [ ] Spring·React가 원본 CSV가 아니라 `profiles.json` 스키마에만 의존하는가
- [ ] 집단 지표 계산이 Python 밖(Java·TS)에 중복 구현되지 않았는가
- [ ] 큰 의존성(ORM, DB, 상태관리, CSS 프레임워크)이 상의 없이 추가되지 않았는가

## 4. 체크리스트 — 일반 코드 품질

- 버그, 예외 처리 누락, 경계값 (빈 배열, 단일 연령구간, 카테고리 1개)
- 지표 계산 로직의 단위 테스트, 특히 0 나누기·결측·연령 누락 케이스
- 계산 로직과 UI 분리
- 보안 (입력 검증, 비밀값 하드코딩)
- 반응형 화면 깨짐
- 가독성, 중복 코드 — 단, 이것만으로 **높음**을 주지 않는다

취향 차이(변수명 스타일, 사소한 포맷)는 지적하지 않거나 **낮음**으로 둔다.

## 5. `docs/REVIEW.md` 작성 형식

이전 라운드는 지우지 말고 **새 라운드를 맨 위에 추가**한다.

```markdown
## 라운드 N — 리뷰 대상: <시작커밋>..<끝커밋> (YYYY-MM-DD)

### 요약
한두 줄로 전체 평가.

### 지적 사항
- **R{N}-1 [높음]** `파일경로:줄번호` — 문제 설명
  - 왜 문제인가: (이 문서 몇 장 규칙 위반인지, 예: "3-4 결측을 0으로 처리")
  - 수정 제안: 구체적으로
- **R{N}-2 [중간]** ...
- **R{N}-3 [낮음]** ...

### 이전 라운드 미해결 항목
- R{N-1}-2: [반영 안 함] 사유 검토 결과 → 종결 / 재지적

### 테스트 결과
실행한 명령과 통과/실패 요약.
```

### 심각도 기준
- **높음**: 계산 결과가 틀림, 3장 도메인 규칙 위반, 실제 데이터 유출 위험, 앱이 깨짐, 중간발표 데모를 막음
- **중간**: 특정 상황에서만 발생하는 버그, 테스트 누락, 실제 데이터 교체 시 문제가 될 구조
- **낮음**: 가독성, 소소한 개선

### 종료 조건
**높음·중간이 0개**면 지적 사항 대신 다음과 같이 쓴다.
```
LGTM — 수정 사항 없음 (낮음 N개는 선택 반영)
```

## 6. 자동 리뷰 모드 (`scripts/review.ps1`로 호출된 경우)

비대화식(`claude -p`)으로 호출되므로 질문해도 답할 사람이 없다. 확인이 필요한 내용은 "확인 필요"로 REVIEW.md에 적는다.
- 테스트·빌드 결과를 입력으로 넘겨받았으면 직접 실행하지 말고 그 결과를 "테스트 결과"에 옮긴다. 넘겨받지 못했으면 허용된 테스트 명령을 실행한다.
- `FAILED`인 항목은 **높음**으로 지적한다. `SKIPPED`는 이유를 적고, 환경이 준비돼야 할 단계인데 계속 SKIPPED면 **중간**으로 지적한다.

응답의 **마지막 줄**은 반드시 둘 중 하나로 끝낸다.
```
VERDICT: LGTM                 ← 높음·중간 0개
VERDICT: CHANGES_REQUESTED    ← 높음 또는 중간이 1개 이상
```

---

## 7. 리뷰 태도

- 지적에는 항상 **근거**(규칙 번호, 재현 입력 값, 예상값 vs 실제값)를 붙인다.
- 확신이 없으면 "확인 필요"로 표시하고 질문 형태로 쓴다.
- 기술 스택이나 설계를 바꾸자는 큰 제안은 지적 사항이 아니라 요약 아래 **"제안"** 항목에 따로 적는다.
